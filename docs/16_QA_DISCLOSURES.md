# 16 — Q&A Disclosures (AI Fest 2026)

Prepared answers for the five disclosure areas. Every claim here is traceable to
a file in this repository. If a judge asks "where does that number come from",
the answer is a path, not a recollection.

**Rule for the whole team: if you are not sure, say "that one is simulated" or
"I'd have to check."** Nothing in this project is damaged by admitting a
limitation. It is damaged by one overclaim that turns out to be false.

## 01 — Dataset declarations

### A. Synthetic operational dataset — *self-generated, no licence*

| | |
|---|---|
| **Source** | Generated by `backend/app/simulation/generator.py` |
| **Format** | PostgreSQL rows (buoys, barometric readings, current observations, buoy contacts, vessel trips, incidents) |
| **Purpose** | Calibrate and evaluate the three core models. No real observations exist. |
| **Preprocessing** | Rejection sampling against the municipal water polygon so no vessel or buoy is placed on land; buoys chained at 55–90% of LoRa range so the mesh is connected to shore |
| **Licence** | None required — we generated it |

Every synthetic row is flagged `is_synthetic = TRUE` in the database, and all
three eval scripts filter on that column. This is deliberate: it makes it
impossible to silently mix simulated and real data later.

**Say this plainly:** the barometric time series, current field and vessel trips
are simulated. We inject 6–10 labelled squall events and score the detector
against those labels.

### B. Open-Meteo Historical Weather API — *real, public*

| | |
|---|---|
| **Source** | `https://archive-api.open-meteo.com/v1/archive` |
| **Purpose** | Training data for the marine hazard (danger zone) model |
| **Period** | 2023-08-01 → 2025-12-31 |
| **Volume** | 12,456 training rows / 8,760 test rows |
| **Licence** | Free for non-commercial use, CC-BY 4.0 attribution |

### C. Open-Meteo Marine API (ERA5-Ocean) — *real, public*

Wave height and wave period features. Same licence as above.

### D. NOAA IBTrACS v04r01 — *real, public domain*

International Best Track Archive for Climate Stewardship. Supplies tropical
cyclone tracks used to label 189 of the 1,114 positive rows. US Federal
Government work — public domain. **We recorded the SHA256 of the exact file
used**, which is in `web/ml/model-card.json`.

### E. GEBCO 2020 bathymetry via OpenTopoData — *real, public*

Seabed depth per sector. Note the honest finding: `depth_m` scored **0.0
feature importance**. We kept it in the card rather than quietly dropping it.

### F. Open-Meteo Forecast API — *live, in-product*

Current conditions and the Home seven-day outlook strip
(`mobile/lib/services/forecast_provider.dart`). Displayed with the source
named and an explicit "this is not a PAGASA warning" disclaimer.

**If asked about the red/amber/green day colours, say this:** they are a
client-side threshold heuristic over public forecast data
(`mobile/lib/services/safety_score.dart`), not a model and not an official
call. The authoritative go/no-go is the MDRRMO-set sea condition in the banner
above the card. The thresholds (30/50 km/h gusts, 1.5/2.5 m waves) are our own
provisional numbers and have not been reviewed by MDRRMO or by a fisherman —
that review is listed under known gaps below.

The intended source is a fused backend score combining stationary sensor-buoy telemetry
with the weather feed. The contract for it is written
(`docs/05_PUBLIC_API.md`) and the app already prefers it when present, but the
endpoint is **not built**. Do not describe the colours as buoy-driven today.

### F2. Open-Meteo Marine API — *live, in-product*

Significant wave height for the outlook strip, sampled at a fixed offshore
point because the wave grid has no data over land. When the marine model
returns nothing for a day — which happens in nearshore cells — the app shows
the day's colour with an explicit "sea state not available" note rather than
assuming calm water.

### G. Basemap tiles

OpenStreetMap (ODbL) and ArcGIS Online imagery, attributed in the map control
as required by both licences.

### H. Municipal water polygon

Hand-supplied GeoJSON of New Washington municipal waters, encoded in
`backend/app/geo.py` as the single source of truth for the service area.

## 02 — AI tools & external resources

### Models we built

| Model | Algorithm | Library | Trained on |
|---|---|---|---|
| Marine hazard / danger zone | `GradientBoostingClassifier` | scikit-learn 1.9.0 | **Real** Open-Meteo + IBTrACS + GEBCO |
| Squall nowcasting | `Pipeline(StandardScaler, LogisticRegression)` | scikit-learn 1.9.0 | Synthetic |
| Trip anomaly / overdue | Unsupervised statistical profiling (mean, std, p10/p90 per vessel) — **no ML library** | numpy only | Synthetic |
| Drift prediction | Monte Carlo Lagrangian particle model (leeway + current + diffusion) — **physics, not learned** | numpy | Synthetic; calibrated |

### Libraries

`scikit-learn 1.9.0`, `numpy 2.4.6`, `joblib 1.5.3`,
`fastapi 0.139.2`, `asyncpg`, `PyJWT`, `bcrypt`. Frontend: Leaflet, Chart.js.
Mobile: Flutter/Dart, `sqflite`.

### What we did NOT use

- **No foundation models or LLMs anywhere in the product.** No OpenAI,
  Anthropic, Gemini or HuggingFace inference at runtime.
- No pretrained weights of any kind. Every model here was fitted by us.
- No xgboost, no PyTorch, no TensorFlow.

### AI coding assistants — disclose this

We used AI coding assistants during development. Most hackathons now require
this to be stated, and volunteering it reads far better than being asked.

The honest framing: assistants accelerated implementation, but the architecture,
the model choices, the honesty constraints and the decision about what *not* to
build were ours. Two examples worth having ready — we caught and fixed a
migration bug where SQL comments containing semicolons broke the deploy, and we
rejected a drift-model containment figure of 25% as insufficiently calibrated
rather than reporting it.

### Citation

Sources for the hazard model are embedded in `web/ml/model-card.json` under
`metadata.sources`, with URLs and a checksum. API attributions appear in the
map controls and the mobile weather card.

| Polycarbonate sheet, waterproof pod/relay enclosures, straps | ₱10,000 | — |
| Soldering + development materials | ₱12,000 | — |

The old per-buoy marginal-cost figure is retired. An additional boat pod needs
the Heltec, power system, antenna, and a waterproof strap-on enclosure; an
additional stationary buoy also needs a hull, mooring, and service access. Price
the two deployment types separately after the first enclosure prototype.

### How hardware data feeds the system

- **Barometer → squall nowcasting.** Pressure drop rate across the array is the
  primary feature. This is the one sensor→model path that is fully specified.
- **LoRa (SX1262, 915 MHz) → hybrid transport.** Boat pods send directly to the
  tall shore gateway when possible; stationary buoys can relay when needed. The
  64-byte frame limit is why the SOS de-duplication key is `(vessel_id, client_ts)` rather than a UUID — a UUID will not fit.
- **WiFi SoftAP → phone handoff.** The phone joins the boat pod's local access
  point and POSTs to `/v1/sos`. WiFi is intentionally short range; LoRa carries
  the message from the pod to shore or through an optional relay buoy.

### Be honest about these three

1. **`firmware/buoy/` is empty in this repository.** The firmware is not
   submitted here. Do not imply otherwise.
2. **There is no current sensor on the hardware.** Mooring-tilt current sensing
   (MPU6050) is documented in `docs/07_SCOPE_OUT.md` as optional and explicitly
   *not a deliverable*. The current observations feeding drift prediction in the
   demo are **synthetic**.
3. **Range figures are theoretical.** LoRa 6–8 km and WiFi ~1 km are design
   assumptions from the datasheets. `docs/08_DEMO_AND_STATUS.md` has a field
   range test as an open item. We have not measured it outdoors.

## 04 — Bias & responsible AI notes

### Biases we identified

**1. Synthetic calibration — the big one.** Three of four models are calibrated
and evaluated on data from our own generator. There is a real circularity risk:
we are partly measuring how well the model reproduces our own assumptions.
*Mitigation:* the drift model is physics-informed (published leeway
coefficients, Lagrangian transport) rather than purely fitted, so it carries
real structure independent of our data. Every eval result is tagged
`calibration: "synthetic"` in the output. The 90-day pilot exists specifically
to break this circularity.

**2. Coverage bias runs opposite to risk.** A direct boat-pod link reduces the
need to place a buoy around every phone-contact zone, but low antennas and sea
state can still create dead zones farther offshore. *Mitigation:* test the
direct pod-to-shore link, add relay buoys only where measurements justify them,
and retain fixed sensor buoys where their data has independent value.

**3. Cold-start and irregularity bias in trip profiles.** Anomaly detection
learns each vessel's own pattern, so a new fisher has no baseline, and a fisher
whose habits are genuinely irregular generates more false positives. The risk is
**alert fatigue directed at specific people** — a dispatcher who sees repeated
false alarms from one vessel may deprioritize that vessel's real emergency.
Irregular is not the same as reckless. *Mitigation:* confidence scoring and a
four-stage escalation ladder rather than a binary alarm, so low-confidence
anomalies trigger a silent check-in rather than a dispatch.

**4. Equipment-access bias.** AqOne protects fishers who can use a smartphone
with a boat-mounted safety pod. Fishers without a smartphone, or on a boat
without a pod, may still be outside the primary path. *Mitigation:* make the
pod easy to share and strap on, keep a physical SOS button on the pod, and use
fixed sensor/relay buoys as additional coverage and sensing points where they
already exist.

**5. Hazard labels are environmental proxies, not outcomes.** The danger-zone
model is trained on "was there a cyclone within 350 km, or waves ≥2 m, or gusts
≥40 km/h" — **not** on where vessels were actually lost. It predicts bad weather,
not death. Those correlate, but a calm-water engine failure is invisible to it.
This limitation is already written into `web/ml/model-card.json`; we did not add
it under questioning.

**6. One feature dominates.** `wind_gusts_10m` carries 0.78 of the importance;
`depth_m` carries 0.0. The model is close to a well-calibrated gust threshold
(Brier 0.0216) rather than a rich multivariate model. We report it that way.

**7. Geographic non-transferability.** Trained on Aklan offshore sectors only.
It should not be deployed in another province without retraining, and we would
say so to a buyer.

**8. Surveillance risk.** A safety network that logs vessel positions is one
policy change away from a fisheries-enforcement tool. `docs/07_SCOPE_OUT.md`
records our refusal to build enforcement features — not for lack of time, but
because positioning a safety network as surveillance would destroy adoption
among the people it protects.

### A feature we removed on privacy grounds — worth volunteering

Venture briefly shipped manual fishing-spot reporting: a pin-drop that
published a fisher's exact GPS coordinates, attributed to their vessel, to
every other handset, with no consent step.

We cut it. It contradicted our own design in two places — §6.2 requires
hotspot locations to be spatially binned and protected against exposing an
individual's exact productive location, and §6.1 puts all fisheries
collection behind separate informed consent. A productive fishing spot is
livelihood. Publishing one precisely, for free, to everyone with the app is
not a feature a fisher would have asked for, and the fact that it demoed well
is exactly why it survived as long as it did.

Catch logging already collects species, quantity and position under consent,
which is the input the hotspot model needs. The replacement path is binned
cells from that model, never individual pins. See `docs/05_PUBLIC_API.md`.

**This is a good answer to give before you are asked.** It shows the
governance section is load-bearing rather than decorative.

### Mitigations already in the codebase

These are design decisions a judge can verify:

- `/api/ai/metrics` returns **404, not placeholder numbers**, when the evals
  have not been run. The dashboard shows an empty state rather than inventing
  figures.
- A live SOS is displayed with **no confidence percentage**. A person pressing a
  button is a fact, not a prediction; earlier code coerced the missing score to
  `0`, which would have rendered a distress call as "0% confidence."
- The app's wind indicator is a single 30 km/h threshold, shown with its source
  and an explicit "this is not a PAGASA warning" disclaimer. It is documented as
  "not a model and must never be presented as one."
- "Safe to Go Out" on the dashboard is a **human MDRRMO declaration**, stored
  with the operator's name and rendered as "Last set by {name} at {time}" — not
  an algorithmic verdict.
- Unbuilt PRD sections carry an explicit `[Roadmap — not implemented]` tag.
- Fisherman identity is device-local with no password, by design: a person in
  distress cannot be asked to log in.

### One thing to watch

`trust_tier` distinguishes `registered` from `self_declared` vessels. It must
never be allowed to gate *whether* a distress call is answered — only to inform
context. Worth stating if asked, because it is the obvious place discrimination
could creep in later.

## 05 — Extended architecture detail

### Full path

```
Phone (Flutter, SQLite outbox, works in airplane mode)
   ├── WiFi SoftAP ──► Boat pod (ESP32-S3 + SX1262)
   │                      ├── Direct LoRa ──► Gateway (internet)
   │                      └── Optional relay ──► Stationary buoy ──► Gateway
   └── Direct HTTPS ─────────────────────────────────────────────┐
                                                                  ▼
                                          FastAPI + PostgreSQL (Railway)
                                          ingest → dedupe → event log → AI
                                                                  │
                                                                  ▼
                                          MDRRMO dashboard (Leaflet, 10s poll)
```

### Points worth raising if asked

**Three-path SOS with de-duplication.** Every SOS attempts local storage, the
backend directly when internet is available, and the boat-pod/LoRa path — in
parallel, not in sequence, because waiting out a relay timeout before trying the
internet would delay a distress call for no reason. De-duplication is an
idempotent upsert on
`(vessel_id, client_ts)` with `ON CONFLICT ... DO UPDATE` and a `COALESCE`
merge, so two transports delivering the same emergency produce **one** incident
with the union of what each path knew. The key is that pair rather than a UUID
because a UUID does not fit in a 64-byte LoRa frame.

**The responder loop.** Acknowledging is not a bare flag. The dispatcher enters
an ETA in minutes; the server converts it to an absolute `eta_at` so the
countdown on the handset stays correct however slow delivery is. Once the
promised time passes the app says "delayed — still en route" rather than showing
a negative number, because a countdown expiring into silence reads as "nobody is
coming."

**Hybrid topology.** Boat pods are the primary SOS origin nodes and attempt a
direct LoRa link to the tall shore gateway. Stationary buoys form an optional
relay chain only where direct tests show a gap; their fixed sensor readings are
valuable independently of their relay role.

**Bayesian search re-tasking.** `POST /api/ai/drift/incident/{id}/searched`
applies a searched sector's detection probability to the posterior probability
grid, renormalises, persists it, and returns updated contours. A negative search
result therefore *moves* the search area instead of leaving it static.

**Uncertainty calibration in drift.** Each particle draws a current bias and a
leeway scale factor once at seeding, so the ensemble spreads realistically
instead of collapsing to a single ellipse. Crosswind leeway is assigned
left/right per particle so the search cone can bifurcate — which is what real
leeway models do.

### Known gaps — say these before you are asked

- Buoy firmware is not in this repository.
- No outdoor range test has been performed.
- Live roster / headcount (PRD §5.6) and mass-casualty dispersion (§5.5) are
  **roadmap, not built**. If we cite MV Trisha Kerstin 3, the honest answer is
  that drift prediction and squall alerts would have helped; headcount would
  not have, because we have not built it.
- No LoRa downlink to the handset. The phone learns delivery and acknowledgement
  status over the internet, not over the mesh.
- The forecast strip's safety colours are threshold rules over a public
  weather API, not a trained model and not buoy-derived. The fused
  stationary-sensor + weather scorer is specified but unbuilt, and the thresholds
  themselves are unreviewed by anyone who fishes these waters.
- **There is no hotspot model.** The contract is written
  (`docs/05_PUBLIC_API.md`) and the app renders the layer the moment the
  endpoint answers, but nothing is scored today. If asked what happened to
  the fish-hotspot feature, the answer is that we removed the manual version
  on purpose — see below — and the modelled replacement is Phase 3.
  **The purple cells on the Venture map are invented.** They are shipped so
  the layer can be shown and explained; they are labelled EXAMPLE in the
  legend, drawn in a different colour from the real layer, carry no timestamp
  or reporter counts, and say "NOT real fishing data. Nobody reported these."
  Real cells replace them entirely the moment the endpoint answers. Say this
  before anyone asks — a demo that quietly passes invented data off as model
  output is the thing that would undermine every other honest disclosure in
  this document.
- The Venture compass reads **magnetic** north from the handset magnetometer.
  It is uncorrected for declination (under a degree locally, well inside
  sensor noise) and will read badly near an engine or a magnetic phone mount;
  the dial flags that state but cannot correct it.
