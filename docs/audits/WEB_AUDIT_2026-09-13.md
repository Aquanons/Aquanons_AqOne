# Web audit and review

**Date:** 2026-09-13  
**Baseline:** `master`, commit `c2dd802`, with unrelated mobile changes present.  
**Scope:** The complete `web/` tree, with selected backend routes, tests, and contracts traced where the dashboard depends on them.  
**Result:** Fix the security and operational correctness findings before treating this dashboard as ready for live response.  
**Implementation:** [Five-phase remediation plan](../archive/plans/WEB_REMEDIATION_IMPLEMENTATION_PLAN.md).

Completed 2026-09-14 after resuming the review.
HEAD had advanced to `56868b4`; comparison confirmed no changes to the audited web tree or the backend files cited for SOS provenance and geographic tests.

## Assessment

The plain JavaScript and vendored Leaflet architecture is adequate for this application.
A framework migration, bundler, new state-management library, or WebSocket layer would not resolve the defects found here.
The main problems are unsafe rendering, success messages for actions that do not happen, incomplete-data handling, and runtime integration paths outside the existing tests.

The review found 14 actionable groups: eight P1 findings and six P2 findings.
P1 means fix before live operational use; P2 means fix in the same remediation cycle before release acceptance.
The separate Ponytail section identifies removable complexity without treating required AI, consented activity maps, or safety checks as bloat.

## Correctness and security review

### F01 - P1: Untrusted values reach HTML sinks in the operator session

**Locations:** `web/js/dashboard/dashboard-buoy-health.js:17-35`, `dashboard-emergency-advisory.js:318-339`, and `dashboard-tools.js:43-49`.

The compact incident feed concatenates `a.desc` directly into `innerHTML`.
`dashboard-live-sos.js:115-123` builds that description from the backend's boat name and fisher-entered SOS note.
The main alert list and map tooltip escape their copies, so the shared helper tests pass while this sibling renderer remains unsafe.
The sea-condition renderer similarly inserts `reason` and `set_by_name` directly, and the pin popup interpolates `CURRENT_USER.name`.
Backend authentication does not make stored names or notes safe HTML.

**Reproduction:** Pass an event description containing `<img src=x onerror="auditProbe()">` to the actual compact-feed renderer.
The generated markup preserves the tag and handler; this was reproduced in the isolated probe.
In a browser, this is a script-capable HTML injection sink inside the bearer-token session.
[MDN documents the same innerHTML injection behavior](https://developer.mozilla.org/en-US/docs/Web/API/Element/innerHTML).

**Smallest fix:** Use `textContent` for text-only elements and the existing `AqOneDashboardUtils.escapeHtml` where HTML templates remain necessary.
Trace all callers and all siblings, including sea-condition reason/actor and pin names.
Preserve intentionally constructed badge markup rather than escaping entire rendered components.
Add one regression group covering the actual renderers, not just the escaping helper.

### F02 - P1: Missing weather becomes low risk, and partial marine data can crash rendering

**Locations:** `web/js/dashboard/dashboard-shortcuts-weather.js:76-90,154-197`, `web/js/dangerZonePredictor.js:57-64`.

The weather renderer converts null measurements with `Number`, then defaults missing wind/gust values to zero before classification.
Null wind, gust, wave height, and period render **MODEL: LOWER RISK**, as confirmed by the probe.
The hazard classifier also accepts all-null features because `Number(null)` is finite.
Missing wave period with a valid height causes `wavePeriod.toFixed(1)` to throw.
Thunderstorm codes are displayed as conditions but do not participate in the current weather risk classification.

**Reproduction:** Render null measurements, then render `{wave_height: 1}` with the period omitted.
The first produces a green classification and the second throws.
Feed null values for every declared model feature to `predictProbability`; it returns a number instead of rejecting unavailable inputs.

**Smallest fix:** Validate presence and finite numeric values before coercion, reject physically invalid negatives, and preserve missing values through rendering and inference.
Require sufficient inputs for a lower-risk classification while allowing known adverse evidence to retain its warning.
Format height and period independently.
Use the existing documented risk policy rather than inventing another threshold table during the fix.
Keep source age and partial-data status visible; do not present an incomplete forecast as “no severe thresholds detected.”

### F03 - P1: Populated incident and AI panels fail on missing helper references

**Locations:** `web/js/dashboard/dashboard-incidents.js:80,84`; `dashboard-ai-ops.js:140-143,230-257,416,627-637,719`.

`openIncidentDrawer` calls bare `confidenceColor`, but its only definition is scoped inside `dashboard-vessels-alerts.js` and exported as `ns.confidenceColor`.
The AI module calls `ns._escHtml`, but no module exports that property.
The similarly named advisory helper is local to its own closure.
Real SOS drawers with null confidence avoid the first bug, and empty AI responses avoid many instances of the second, explaining why empty-data checks can look healthy.

**Reproduction:** Open a scored overdue incident, and render one AI risk row.
The probes produced `ReferenceError: confidenceColor is not defined` and `TypeError: ns._escHtml is not a function`.

**Smallest fix:** Bind the existing `ns.confidenceColor` and use the already available `ns.escapeHtml` throughout the AI module.
Do not introduce another escaping implementation or a dependency-injection layer.
Exercise populated risk rows, drift metadata, searched-sector notes, and scored drawers in the runtime gate.

### F04 - P1: Active squall rendering calls a method its Leaflet group does not have

**Locations:** `web/js/dashboard/dashboard-ai-ops.js:11,731-788`.

`aiSquallLayer` is created with `L.layerGroup()` and later receives `getBounds()` whenever there is a detection.
`getBounds` belongs to `FeatureGroup`, not `LayerGroup`.
An empty squall response returns before this path, so the failure appears when an actual warning needs rendering.
The API-shaped runtime probe reproduced the exception; the [Leaflet reference](https://leafletjs.com/reference.html#featuregroup-getbounds) confirms the required group type.

**Smallest fix:** Use the existing Leaflet `featureGroup` for this bounds-bearing collection, then test an active polygon and a detection without a polygon.
Verify that failure in one auxiliary renderer cannot reset otherwise loaded risk/drift panels through the broad initialization catch.

### F05 - P1: Live incident controls claim that unsent messages were delivered or queued

**Locations:** `web/js/dashboard/dashboard-incidents.js:391-397`; `web/html/dashboard.html:852-854`.

“Broadcast to Nearby Vessels” only sets text saying a broadcast was sent to three vessels.
“Request Silent Check-in” only sets text saying a request was queued.
Neither invokes a transport or backend API, and neither handler is restricted to demo incidents.
The broadcast success was reproduced by invoking its actual click handler with no network implementation.

**Smallest fix:** Remove or disable these controls in the operational interface and state that the capability is unavailable.
If retained for a deliberate demo, label the outcome as simulated.
Do not build a broadcast system or LoRa handset downlink to make this stub true: the PRD treats nearest-responder broadcast as roadmap work and the shared scope excludes handset downlink.

### F06 - P1: The standalone advisory page reports a nonexistent dispatch queue

**Locations:** `web/html/createAdvisory.html:245-300`; `web/js/advisoryService.js:29-42` for the existing supported client.

The standalone form sends no bearer token to the protected advisory endpoint.
Any HTTP or network failure then writes to `aqone_advisories` in localStorage and displays a successful queued-for-dispatch message.
Repository search found no consumer or retry worker for that storage key.
Success and failure both redirect to `index.html` under `/html/`, which does not exist.
This page is directly reachable even though it has no current incoming application link.

**Reproduction:** Open the standalone URL while signed in and submit against the default endpoint.
Inspect the missing Authorization header; simulate 401 or network failure and observe the fallback success path.
This flow was established by source tracing, not a live advisory submission.

**Smallest fix:** Replace the obsolete standalone form with a compatibility redirect/link to the dashboard's existing advisory workflow.
Alternatively, if the standalone page is explicitly required, reuse `AdvisoryService` and keep failures as failures.
Do not create an outbox subsystem solely to justify this message.

### F07 - P1: SOS polling can replace newer state with older data

**Locations:** `web/js/dashboard/dashboard-live-sos.js:194-239,250-251`; `dashboard-incidents.js:143-156`.

The three-second interval permits overlapping requests, and every response replaces the shared live-alert array without an ordering guard.
The probe resolved request B with SOS 2 and then the older request A with SOS 1; the display state reverted to SOS 1.
The stale response also receives a fresh success timestamp.
A response without `events` is accepted as an empty success, while a non-array `events` can clear the old array before `.map` fails.
An open drawer is left actionable when its event disappears from the authoritative active list.

**Smallest fix:** Serialize polling or use a per-feed request generation, validate and map the complete response before replacing state, and only advance freshness after an accepted result.
Close or explicitly retire a drawer whose event has left the active feed.
Retain three-second polling unless a separately measured requirement calls for SSE.
Verify delayed requests across acknowledge/resolve and malformed responses, not just normal arrival order.

### F08 - P1: Demo provenance is lost across live-data paths

**Locations:** `web/js/dashboard/dashboard-live-sos.js:115-123`; `backend/app/api/sos.py:203-239`; `web/js/demo-control.js:16-17`; `web/js/dangerZonePredictor.js:11-16`; `dashboard-markers.js:364-376`.

Every SOS read from `/api/sos/active` is assigned `isLive: true`.
The backend has synthetic SOS rows, written by `backend/app/demo/scenarios.py`, but the active endpoint neither excludes them nor returns their `is_synthetic` field.
Consequently a synthetic server event is indistinguishable from a real distress call in this UI.
Separately, merely opening the demo controller persists weather/marine endpoint overrides in origin-wide localStorage.
The predictor consumes those overrides on later dashboard visits while its result copy continues to say live weather/marine data.
Whether an overridden request succeeds depends on the demo backend configuration; the persistence and missing provenance are definite.

There is already a global demonstration banner, a sample disclaimer in Stats, and simulated values in buoy popups.
Those are useful, but do not correct a per-event LIVE badge or an indefinitely retained demo endpoint.
The condensed incident feed also omits a DEMO badge for its sample rows.

**Smallest fix:** Update the public contract first, then either exclude synthetic SOS from the operational endpoint or return explicit provenance and render it consistently.
Scope demo weather configuration to an explicit demo session and clear it on exit; avoid global persistent overrides affecting ordinary operation.
Add DEMO/sample labeling at the condensed feed and buoy-health surfaces, and replace their page-load-based “Last synced” claim with honest sample status.
This is provenance repair, not a request to implement the roadmap live roster.

### F09 - P2: Feed failures and acknowledged incidents can look like an all-clear

**Locations:** `web/js/dashboard/dashboard-ai-ops.js:599-606,866-868,912-920`; `dashboard-trip-checks.js:26-39`; `dashboard-vessels-alerts.js:256-268`; `dashboard-shortcuts-weather.js:290-294,381-414`.

The AI risk failure handler renders an empty list, using the same “No active vessel risk rows available” output as a successful empty response.
Trip checks and squall warnings retain old content after failures, but have no independent client freshness transition; their displayed ages can freeze while the SOS header remains LIVE.
Weather caches have no age limit, and a stale snapshot retains its colored risk badge.
The SOS status label says ALL CLEAR whenever there are no unacknowledged rows, even if acknowledged, unresolved incidents remain, including a fisher reporting continued danger.

**Smallest fix:** Reuse `classifyFreshness` per safety feed, distinguish unavailable from successfully empty, and preserve warnings with explicit age.
Replace ALL CLEAR with a precise label such as “No unacknowledged SOS” and expose unresolved counts.
Expire positive low-risk claims under an agreed freshness policy without hiding known adverse evidence.
These changes need no generic polling framework.

### F10 - P2: Profile and password controls represent local placeholders as account changes

**Locations:** `web/js/profile.js:359-390,405-434,483-526`; `web/html/Systemprofile.html:75-110,162-179,280-292`.

Password submission checks strings, clears the fields, and announces success without calling an API.
Personal details are stored under one origin-wide `aqone_profile_data` key, which is reapplied regardless of the signed-in user.
The page starts with a hardcoded administrator identity, statistics and session details rather than loading the authenticated account.
Email-notification and SOS-sound preferences have no corresponding behavior wired here.

**Smallest fix:** Load identity from the existing authenticated account endpoint/session and remove unsupported password, notification, avatar, and account-editing promises.
Show browser-local preferences as browser-local preferences; scope any retained user data to the account.
A real password-management API is a separately scoped feature, not required to make the current UI honest.

### F11 - P2: Login mutates passwords and leaves demo session state behind

**Locations:** `web/js/script.js:36-68`; `web/js/admin-signup.js:37-40`; `web/js/dashboard/dashboard-core.js:93-116`.

Admin signup submits the password unchanged, but login trims it.
An account created with a leading or trailing space in its password cannot log in with that same password through this form.
Successful login does not clear `aqoneDemoBypassActive`, and the shared session-clear function does not remove it either.
After entering demo mode and subsequently logging in, a later real 401 can be treated as a demo failure rather than an expired session.
This does not bypass backend authorization; it misrepresents session state and suppresses normal recovery.

**Smallest fix:** Preserve password bytes, clear demo flags when entering or clearing a real session, and keep unsupported profile changes out of this patch.
Test a whitespace-bearing password and demo-to-real-to-expired transitions.

### F12 - P2: Modal keyboard behavior does not protect the active incident workflow

**Locations:** `web/js/dashboard/dashboard-shortcuts-weather.js:18-50`; `dashboard-incidents.js:195-203,239-244`; `web/html/dashboard.html:862-903`.

Global shortcuts exclude only INPUT elements, so typing letters such as `f`, `p`, or `m` into responder notes and other TEXTAREAs triggers map actions.
Escape closes the SOS drawer before checking the acknowledgment overlay, and the overlay is not handled by that shortcut code.
The acknowledgment dialog has a dialog role and initial focus, but no focus containment or restoration.
The case ID is read from mutable drawer state at confirmation time rather than captured when the dialog opens.
If another drawer becomes active, the displayed modal target and submitted ID can diverge; this interaction needs a browser reproduction during implementation.

**Smallest fix:** Ignore shortcuts in all editable elements and while a modal is active.
Capture the acknowledgment target when opening the modal and prevent background case switching while it is open.
Use native dialog behavior where it fits the existing UI, or implement the minimal focus containment, Escape close, and focus return in the existing modal functions.
Verify keyboard-only completion and cancellation, plus no-GPS incidents and modal state across polling.

### F13 - P2: Audit results, pagination, exports and case timelines can disagree

**Locations:** `web/js/dashboard/dashboard-operations-audit.js:29-50,80-101,121-156,179-181`.

Each page/export request rebuilds filters from the current form controls rather than an immutable copy of the applied search.
Editing the form without submitting and then loading more combines an old cursor with new filters; exporting can produce a different dataset from the displayed applied filters.
Concurrent searches can finish out of order, and a late timeline response for case A can populate the drawer already titled for case B.

**Smallest fix:** Capture applied filters on search submission, reset pagination for each search, and use that same snapshot for page loads and exports.
Disable duplicate page loads and use small request-generation guards for search and per-case timelines.
Check two delayed searches and two quick case selections with reversed response order.

### F14 - P2: Runtime verification and secondary UI wiring are incomplete

**Locations:** `backend/tests/test_dashboard_coords.py:21-39`; `web/test/dashboard-utils.test.js`; `web/js/dashboard/dashboard-profile-pill.js:21-41`; `dashboard-buoy-health.js:257-273`; `dashboard-tools.js:501-508`; `dashboard-vessels-alerts.js:80-83`.

The geographic test still reads removed `web/js/dashboard.js`, so it cannot check the current split modules.
The sole web test file exercises helper functions, not module initialization, click handlers, request races, or HTML integration.
The export button has two handlers; the second references undefined `facilities` and throws after the first handler starts a download.
Squall/drift toggles control the core's empty `squallLayer`/`driftLayer`, whereas the actual AI overlays live in different groups created by the AI module.
The vessel sort uses `priority || 9`, so priority zero for overdue vessels becomes nine and sorts behind less urgent rows.

**Smallest fix:** Delete the duplicate export handler, bind layer controls to the actual rendered groups, use nullish defaulting for priority, and update the coordinate test to the actual module files.
Keep the helper tests and add a small runtime regression file using the existing Node test runner.
Add a browser acceptance gate with populated fixtures and failed requests.
Do not present syntax checking as a full JavaScript lint pass; there is currently no web package manifest or configured web linter.

## Keep, and defer

- Keep plain HTML/CSS/JavaScript, Leaflet, native fetch, URLSearchParams, the shared escaping/freshness utilities, and Node's built-in test runner.
- Keep the implemented AI/drift/SAR and consented coarse activity-map functionality; the PRD includes these capabilities.
  Experimental-model caveats and training provenance are useful safeguards, not bloat.
- Keep polling while fixing ordering and freshness; this audit provides no evidence that switching transport is necessary.
- Do not delete `signup.html` merely because it redirects; it intentionally preserves older registration links.
- Do not blindly rewrite the 5,660-line dashboard stylesheet.
  Remove confirmed dead assets first and require rendered checks before consolidating cascade-sensitive overrides.
- Do not count the 13.9 MB background video as a dashboard network-performance defect merely because it exists on disk.
  Asset reachability and distribution cleanup can be checked separately.
- Do not add roadmap live-roster, broadcast, photo, account-management, or new AI-model work to make decorative controls functional.
- Do not claim current deployment readiness from the old status table, or infer that hardware steps have passed from the web unit tests.
